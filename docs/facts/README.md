# Конвейер обработки фактов

Порядок работы ровно такой, как договорились: сначала находим материал, затем переводим его
в машиночитаемую форму, затем модели анализируют и выделяют важное для себя, затем сравниваем
и собираем итоговый документ.

| шаг | что делает | файл | команда |
|---|---|---|---|
| 1. Найти материал | 7 колод, 260 страниц, 653 факта; тематических 119 | `docs/registry/page_facts.json` | `docs/registry/tools/unused_relevant.py` |
| 2. Машиночитаемая форма | факт = строка JSON со стабильным id, координатами и признаком темы | `docs/facts/facts.jsonl` | `python3 docs/facts/build_facts.py` |
| 3. Анализ моделями | каждая модель выбирает значимые факты и пишет выводы со ссылками на них | `docs/facts/runs/<колода>.<backend>-<штамп>.json` | `python3 docs/facts/run_analysis.py --backend zcode --deck inkofood-2026` |
| 4. Сравнение | кто что выбрал, где сошлись, где разошлись, какие выводы совпали | `docs/facts/COMPARISON.md`, `COMPARISON.json` | `python3 docs/facts/compare_analyses.py inkofood-2026` |

## Формат факта

```json
{"fact_id": "F-1a2b3c4d5e6f", "deck": "inkofood-2026", "page": 34,
 "label": "Дата производства и срок годности на лицевой стороне упаковки",
 "value": "61,7 %", "thematic": true, "deck_sha256": "…"}
```

`fact_id` выводится из содержимого (колода, страница, подпись, значение): повторная сборка
не плодит дублей и не сдвигает номера при добавлении колод.

## Формат ответа модели

Строгий JSON, только он идёт в сравнение:

```json
{"selected":    [{"fact_id": "F-…", "why": "чем важен"}],
 "conclusions": [{"text": "вывод", "fact_ids": ["F-…"]}],
 "not_relevant":[{"fact_id": "F-…", "why": "почему не значим"}]}
```

Прогон принимается, если все `fact_id` существуют в `facts.jsonl`, есть выводы и у каждого вывода
есть ссылки. Иначе прогон сохраняется с пометкой `problems` и в сравнение идти не должен.

## Почему сравнение устроено именно так

Модели выделяют важное для себя — значит расхождение выбора это сигнал, а не ошибка. Поэтому
сравнение не вычитает одно из другого, а считает четыре среза: выбрали все, выбрало большинство,
выбрал ровно один (повод проверить, не пропуск ли это), не выбрал никто (кандидаты в малозначимые
и в пропущенные). Выводы кластеризуются по пересечению `fact_ids` и по близости текста (порог 0.55):
так одинаковые по смыслу формулировки собираются вместе, а разные не склеиваются.

Итоговый документ собирается из этих срезов человеком: согласие всех — основа, расхождения —
пункты, которые надо решить, «не выбрал никто» — проверка на слепые зоны.

## Решения по фактам: справочно, в выводы, снять

После сравнения у каждого спорного факта появляется решение, и оно записывается, а не помнится:

| файл | что это |
|---|---|
| `fact_decisions.json` | решение по факту: `info` / `conclusions`, с причиной, колодой, страницей и id требования, если оно есть |
| `apply_fact_decisions.py` | применяет решения и собирает `reviews/2026-10-25-inkofood/APPENDIX-INFO.md` — приложение «Справочно» |
| `docs/registry/dispositions.json` | те же решения в терминах требований, для `apply_dispositions.py` |

Приложение «Справочно» — не свалка: каждый факт в нём стоит с колодой, страницей, числом и
причиной, почему он не опора выводов. Предикат `conclusions` ищет факт в выводах, предикат
`info` — только в этом приложении, поэтому «обозначено для информации» проверяемо, а не декларативно.

Текущее состояние решений: 9 фактов разобрано после слепых зон — 8 справочно, 1 в выводы
(Брестский мясокомбинат: знают 89 %, покупают 66,5 %). Из 9 требований 7 затронуто.

## Связь с реестром обязательств

Реестр требований (`docs/registry/`) — отдельный слой: он отвечает не «что модели показалось важным»,
а «что обязано быть в итоговых выводах». Факты этого конвейера могут становиться требованиями
(`REQ`), но не автоматически: сначала решение о значимости, потом регистрация.
